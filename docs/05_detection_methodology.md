# 05 Detection Methodology

## 1. What detection claims

SentinelBridge evaluates the evidence it is given. It asks:

> Does the supplied evidence demonstrate that this security condition exists?

It does not ask whether Florence's environment is secure. Evidence is simulated, and the engine does not verify any external system.

Detection, risk, framework mapping, remediation, and business decision are separate stages. A detector result is never a risk rating or a decision.

---

## 2. Status model

| Status | Meaning | evidence_status | severity |
|---|---|---|---|
| PASS | Evidence demonstrates the requirement is met | sufficient | none |
| FAIL | Evidence demonstrates the requirement is not met | sufficient | the control's fixed severity |
| INSUFFICIENT | Evidence is missing, incomplete, unknown, or cannot decide the question | insufficient | none |
| INPUT_ERROR | Input violates the schema or evidence rules | invalid | none |

Absence of evidence is never a FAIL.

---

## 3. Rules that apply to every detector

### 3.1 Coverage
Each detector produces one finding per applicable asset.

- An applicable asset is an asset in `company/asset_inventory.yaml` whose category is in the control's `applies_to`.
- For CTRL-DATA-001 and CTRL-DATA-002, the asset's tier must also be marked sensitive.
- An applicable asset with no evidence gets an INSUFFICIENT finding. No asset is silently skipped.
- Finding IDs follow the detector key, numbered in inventory order: `FND-MFA-01`, `FND-CLOUD-EXPOSURE-01`, `FND-CLOUD-EXPOSURE-02`.

### 3.2 Order of evaluation
1. Validation (INPUT_ERROR, see 3.8).
2. Exclusions: records covered by a control exception are not evaluated.
3. Sufficiency: can each remaining record be decided? A confirmed violation counts as decided.
4. Rule: does the record meet the requirement?

### 3.3 Aggregation per asset
Each record is PASS, FAIL, unevaluable, excluded by a documented exception (listed under each control's Exceptions), or out of scope. The asset result is:

1. FAIL if any record is FAIL. Unevaluable records are mentioned in the description.
2. Otherwise INSUFFICIENT if any record is unevaluable.
3. Otherwise PASS if at least one record passed, or if every record was excluded by a documented exception. In the second case the description says so, for example "excluded: stateless".
4. Otherwise INSUFFICIENT: the asset has no records, or none are in scope and none are excluded by an exception.

One special case: for CTRL-NET-001, a non-empty rule list with no administrative-port rules is PASS, because the full rule set shows no such exposure.

### 3.4 Sufficiency
A record is unevaluable when a mandatory field is missing, null, or `unknown` and the fields that are present do not already confirm a violation. A confirmed violation always wins. A missing evidence block or an empty record list makes the asset INSUFFICIENT.

### 3.5 Time
All time arithmetic is measured against the evidence's `collected_at`, never the wall clock. Samples therefore give the same result whenever they are run.

- `detected_at` is still generated by the engine at run time.
- The MVP does not reject evidence for being old relative to the run time. Staleness is handled by control thresholds (logging silence, backup age, last login). This limitation goes in `docs/07_assumptions_and_limitations.md`.

### 3.6 Data tier
A tier is declared only in `company/asset_inventory.yaml`. Evidence records carry an `asset_id`, never a tier. Detectors look the tier up. "Sensitive" means the tier is marked `sensitive: true` in `company/data_classification.yaml`.

### 3.7 Severity
A FAIL finding takes the fixed `severity_on_fail` from `controls/security_controls.yaml`. Severity labels the finding. It is not risk. Likelihood and impact are assessed in Phase 2.

### 3.8 INPUT_ERROR
The validator runs before any detector.

- Schema checks: required fields, types, enumerations, ID formats, ISO 8601 timestamps, value ranges.
- Evidence checks: `asset_id` exists in the inventory, `record_id` values are unique, `collected_at` is present.
- One invalid record rejects the whole input. The result is a pipeline-level INPUT_ERROR with `detector_id: null`, and no detector runs.
- The INPUT_ERROR result uses the finding record format: `finding_id` FND-INPUT-01, null detector, control, and asset, an `errors` list, and `assessment_id` ASM-UNKNOWN if the input has no valid one.
- Missing, null, or `unknown` values are not schema errors. They pass validation and become INSUFFICIENT. Only values that are present and malformed cause INPUT_ERROR.

### 3.9 Accepted risk
Accepting a risk does not turn a FAIL into a PASS. The condition still exists. Treatment is decided in Phase 2.

### 3.10 Finding content
`evidence_ref` lists the records behind the result as `block:record_id`, for example `identity:ACC-0007`. `description` states the rule applied and the counts, for example "3 of 12 privileged human accounts do not have MFA enforced."

## 4. Evidence value conventions

These are the allowed values. The input schema (step 5) encodes them.

| Field | Allowed values |
|---|---|
| account_type | human, service, break_glass, seasonal |
| account_status | enabled, disabled |
| mfa_enrollment_status | enrolled, not_enrolled, unknown |
| mfa_enforcement_status | enforced, not_enforced, unknown |
| authentication_source | local, federated |
| encryption_status | enabled, disabled, unknown |
| key_management | customer_managed, provider_managed, none |
| protocol (flows) | https, tls, http, ftp, telnet, other |
| flow_scope | external, internal |
| protection_mechanism | tls, mtls, service_mesh, none |
| vendor_support_status | supported, extended_support, end_of_life, unknown |
| risk_acceptance_status | none, accepted |
| installation_status | installed, not_installed, unknown |
| protection_status | active, inactive, unknown |
| definition_update_status | current, outdated, unknown |
| endpoint_scope_status | in_scope, ephemeral, out_of_scope |
| source_status | active, inactive, unknown |
| audit_configuration | enabled, disabled, unknown |
| public_access_status | public, private, unknown |
| last_backup_status | success, failed, unknown |
| immutability_status | protected, unprotected, unknown |
| statefulness | stateful, stateless, unknown |
| access_mechanism | direct, vpn, ztna, reverse_proxy, bastion |
| Booleans | privileged_status, complexity_requirements, required_source, mfa_required |

The identity block holds two record lists: `accounts` and `password_policies`.

## 5. Controls

Constants named in capitals live at the top of each detector module.

### CTRL-IAM-001 Privileged Accounts Without MFA
Detector DET-MFA. Severity on FAIL: critical. Evidence: `identity.accounts`.

- **In scope:** accounts with `account_type` human or break_glass and `privileged_status` true.
- **Mandatory:** user_id, account_type, privileged_status, mfa_enrollment_status, mfa_enforcement_status.
- **PASS:** every in-scope account is enrolled and enforced.
- **FAIL:** any in-scope account is not_enrolled or not_enforced.
- **INSUFFICIENT:** no identity evidence, no in-scope account, or an unknown or missing mandatory field with no confirmed FAIL.
- **INPUT_ERROR example:** `mfa_enforcement_status` is "yes".
- **Exceptions:** service accounts are excluded and need separate key and certificate controls.
- **Assumption:** break-glass accounts are privileged human accounts and are not exempt from MFA.

### CTRL-IAM-002 Excessive User Privileges
Detector DET-EXCESS-PRIV. Severity on FAIL: medium. Evidence: `identity.accounts`.

- **In scope:** accounts with `account_type` human.
- **Mandatory:** user_id, account_type, assigned_permissions, used_permissions, resource_scope, usage_period (days).
- **Optional:** administrative_status (informational, reported in the description).
- **Excess permissions:** assigned permissions that are neither used within the usage period nor listed in `resource_scope`.
- **PASS:** every in-scope account has excess permissions within `MAX_EXCESS_PERMISSIONS` (0).
- **FAIL:** any in-scope account exceeds that limit.
- **INSUFFICIENT:** an account's `usage_period` is below `USAGE_WINDOW_DAYS` (90), a mandatory field is missing, or no evidence, with no confirmed FAIL.
- **INPUT_ERROR example:** `assigned_permissions` is a string, not a list.
- **Exceptions:** break_glass accounts are excluded and handled under documented emergency-access rules. Service accounts are excluded.
- **Assumption:** `resource_scope` lists the permissions approved for the account's role or resource scope.

### CTRL-IAM-003 Inactive Enabled Accounts
Detector DET-INACTIVE-ACCT. Severity on FAIL: medium. Evidence: `identity.accounts`.

- **In scope:** enabled accounts with `account_type` human.
- **Mandatory:** user_id, account_type, account_status, and last_login. `last_login` may be null if `account_creation_date` is present.
- **Optional:** password_last_set (informational).
- **Inactivity:** days from `last_login` (or from `account_creation_date` if the account never signed in) to `collected_at`.
- **PASS:** every in-scope account is within `INACTIVITY_DAYS` (90).
- **FAIL:** any in-scope account exceeds it.
- **INSUFFICIENT:** both `last_login` and `account_creation_date` are missing, no evidence, or no in-scope account.
- **INPUT_ERROR example:** `last_login` is not a valid ISO 8601 timestamp.
- **Exceptions:** service, seasonal, and break_glass accounts are excluded through `account_type`. Disabled accounts are out of scope.

### CTRL-IAM-004 Password Policy Violations
Detector DET-PASSWORD. Severity on FAIL: medium. Evidence: `identity.password_policies`, one record per tenant or domain.

- **In scope:** policies with `authentication_source` local.
- **Mandatory:** tenant_or_domain, authentication_source, minimum_password_length, complexity_requirements, maximum_password_age (days, 0 means never expires), lockout_configuration (threshold, 0 means no lockout).
- **Optional:** password_last_set (informational).
- **Baseline:** `MIN_PASSWORD_LENGTH` 12, `COMPLEXITY_REQUIRED` true, `MAX_PASSWORD_AGE_DAYS` 365, `MAX_LOCKOUT_THRESHOLD` 10.
- **PASS:** every in-scope policy meets all four.
- **FAIL:** any in-scope policy misses any of them.
- **INSUFFICIENT:** a mandatory field is missing, no evidence, or no local policy in scope.
- **INPUT_ERROR example:** `minimum_password_length` is -1.
- **Exceptions:** federated identities are not evaluated against local password rules.

### CTRL-DATA-001 Sensitive Data Unencrypted at Rest
Detector DET-ENC-REST. Severity on FAIL: high. Evidence: `data_protection.at_rest`, one record per data store.

- **Applicable assets:** customer_database, cloud_storage, backup_systems with a sensitive tier.
- **Mandatory:** resource_id, resource_type, encryption_status, key_management. When encryption is enabled, key_id and encryption_algorithm are also mandatory.
- **Baseline:** `APPROVED_ALGORITHMS` ["AES-256"], `CMK_REQUIRED_TIERS` ["tier_1"].
- **PASS:** encryption enabled, approved algorithm, key_id present, and customer_managed keys for tier_1 (tier_2 may use customer_managed or provider_managed).
- **FAIL:** encryption disabled, algorithm not approved, or a tier_1 store without a customer-managed key.
- **INSUFFICIENT:** encryption_status unknown, a mandatory field missing, or no evidence.
- **INPUT_ERROR example:** `encryption_status` is "maybe".
- **Exceptions:** none defined in the MVP.

### CTRL-DATA-002 Sensitive Data Unencrypted in Transit
Detector DET-ENC-TRANSIT. Severity on FAIL: high. Evidence: `data_protection.in_transit`, one record per flow. The record's `asset_id` is the asset whose data is carried.

- **Applicable assets:** payment_application_infrastructure, customer_database, cloud_storage with a sensitive tier.
- **Mandatory:** source, destination, port, protocol, flow_scope, protection_mechanism. For https and tls flows, tls_version and cipher are also mandatory.
- **Baseline:** `MIN_TLS_VERSION` 1.2, `CLEARTEXT_PROTOCOLS` [http, ftp, telnet], `WEAK_CIPHER_MARKERS` [RC4, 3DES, NULL, EXPORT].
- **PASS:** every flow uses TLS at or above the minimum with no weak cipher, or is internal and protected by mtls or service_mesh.
- **FAIL:** cleartext protocol, TLS below the minimum, weak cipher, or an internal flow with `protection_mechanism` none.
- **INSUFFICIENT:** protocol is other, tls_version or cipher missing on a TLS flow, a mandatory field missing, or no flows listed.
- **INPUT_ERROR example:** `port` is 70000.
- **Exceptions:** protected internal service-to-service flows may rely on mTLS or service mesh.

### CTRL-END-001 Unsupported or Vulnerable Software
Detector DET-VULN-SW. Severity on FAIL: high. Evidence: `vulnerability.software`, one record per installed software item.

- **Applicable assets:** payment_application_infrastructure, employee_endpoints.
- **Mandatory:** asset_id, software_name, version, vendor_support_status. If `cve` is present, `cvss` is mandatory.
- **Optional:** end_of_life_date (informational), risk_acceptance_status (none or accepted, reported in the description, see 3.9).
- **Baseline:** `CVSS_FAIL_THRESHOLD` 7.0.
- **PASS:** every item is supported or on extended_support, and has no CVE at or above the threshold.
- **FAIL:** any item is end_of_life, or has a CVE with cvss at or above the threshold.
- **INSUFFICIENT:** vendor_support_status unknown, cvss missing for a CVE, or no evidence.
- **INPUT_ERROR example:** `cvss` is 11.5.
- **Exceptions:** vendor extended support counts as supported. Accepted risk follows rule 3.9.

### CTRL-END-002 Missing Endpoint Protection
Detector DET-ENDPOINT. Severity on FAIL: high. Evidence: `endpoint.devices`, one record per device.

- **Applicable assets:** employee_endpoints (onsite and remote fleets).
- **Mandatory:** device_id, hostname, device_type, installation_status, protection_status, definition_update_status, endpoint_scope_status.
- **PASS:** every in-scope device is installed, active, and current.
- **FAIL:** any in-scope device is not_installed, inactive, or outdated.
- **INSUFFICIENT:** any of the three statuses is unknown with no confirmed FAIL, or no devices.
- **INPUT_ERROR example:** `ip` is not a valid address.
- **Exceptions:** devices with `endpoint_scope_status` ephemeral or out_of_scope are excluded.

### CTRL-LOG-001 Inadequate Security Logging and Monitoring
Detector DET-LOGGING. Severity on FAIL: medium. Evidence: `logging.sources`, one record per log source.

- **Applicable assets:** security_logging.
- **In scope:** sources with `required_source` true.
- **Mandatory:** log_source, log_type, last_received_timestamp, source_status, audit_configuration, required_source, expected_ingestion_rate, observed_ingestion_rate (events per hour).
- **Baseline:** `MAX_SILENCE_HOURS` 24, `MIN_INGESTION_RATIO` 0.5.
- **PASS:** every required source is active, audit enabled, heard within the silence limit, and ingesting at or above the ratio.
- **FAIL:** any required source is inactive, has audit disabled, has been silent too long, or ingests below the ratio.
- **INSUFFICIENT:** a status is unknown, a timestamp is missing, or no required source is listed.
- **INPUT_ERROR example:** `expected_ingestion_rate` is negative.
- **Exceptions:** none defined. The MVP uses thresholds, not anomaly detection.

### CTRL-CLD-001 Exposed Cloud Storage Containing Sensitive Data
Detector DET-CLOUD-EXPOSURE. Severity on FAIL: critical. Evidence: `cloud_storage.buckets`, one record per storage resource.

- **Applicable assets:** cloud_storage.
- **Mandatory:** storage_id, public_access_status, acl_configuration. `dlp_findings` (a list of data types found, empty if none) is mandatory when the bucket is public and its tier is not sensitive.
- **Sensitive** means the asset's tier is sensitive, or `dlp_findings` is not empty.
- **Outcome per bucket:**

| Public access | Sensitive | Result |
|---|---|---|
| private | any | PASS |
| public | yes | FAIL |
| public | no, DLP scan present | PASS, noted as public with no sensitive data found |
| public | no, DLP scan missing | INSUFFICIENT |
| unknown | any | INSUFFICIENT |

- **Precedence:** DLP findings of sensitive data override a non-sensitive declared tier, so the bucket FAILs.
- **INPUT_ERROR example:** `dlp_findings` is a number.
- **Exceptions:** none. Public storage without sensitive data is deliberately a different outcome from public storage with sensitive data.

### CTRL-BCP-001 Inadequate Backup and Recovery Controls
Detector DET-BACKUP. Severity on FAIL: high. Evidence: `backup.coverage`, one record per resource.

- **Applicable assets:** customer_database, cloud_storage, payment_application_infrastructure.
- **Mandatory:** resource_id, statefulness, backup_policy, last_backup_status, last_backup_timestamp, retention (days), immutability_status.
- **Baseline:** `BACKUP_MAX_AGE_HOURS` 24, `MIN_RETENTION_DAYS` 30, `IMMUTABILITY_REQUIRED_TIERS` ["tier_1"].
- **PASS:** a backup policy exists, the last backup succeeded within the age limit, retention meets the minimum, and tier_1 assets are immutable.
- **FAIL:** no backup policy, a failed last backup, an old last backup, short retention, or a tier_1 asset without immutability.
- **INSUFFICIENT:** statefulness unknown, backup status unknown, timestamp missing, or no evidence.
- **INPUT_ERROR example:** `retention` is "a month".
- **Exceptions:** resources with `statefulness` stateless are excluded.

### CTRL-NET-001 Unrestricted Remote Access
Detector DET-REMOTE-ACCESS. Severity on FAIL: critical. Evidence: `access_control.rules`, one record per firewall rule.

- **Applicable assets:** remote_access.
- **In scope:** rules whose `port` is in `ADMIN_PORTS` [22, 3389].
- **Broad exposure:** `source_cidr` is in `BROAD_CIDRS` ["0.0.0.0/0", "::/0"].
- **Mandatory:** firewall_rule, source_cidr, destination, port, protocol, mfa_required, access_mechanism.
- **PASS:** no in-scope rule has broad exposure, or broad rules use a controlled mechanism (vpn, ztna, reverse_proxy, bastion) with `mfa_required` true. A non-empty rule list with no in-scope rule is also PASS.
- **FAIL:** an in-scope rule has broad exposure with `access_mechanism` direct, or uses a controlled mechanism with `mfa_required` false.
- **INSUFFICIENT:** port or source_cidr missing or unknown, or no rules listed.
- **INPUT_ERROR example:** `source_cidr` is "0.0.0.0/33".
- **Exceptions:** approved controlled mechanisms are treated differently only when the evidence shows MFA is required.
- **Limitation:** only the literal any-address range is treated as broad. Other very wide ranges are not flagged.

## 7. Assumptions

1. Evidence is simulated and supplied as structured JSON.
2. Every evidence record carries an `asset_id` from the inventory and a unique `record_id`.
3. Thresholds are project baselines, defined as constants in each detector module.
4. Detection reports what the evidence shows. It does not verify external systems.
5. Production use would need live integrations, richer exception handling, and human review.
